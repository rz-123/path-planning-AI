# 项目难点：AI 行程地图路线可视化

---

## 面试一句话总结

> 从零实现了行程地图路线功能，解决了两大难点——**坐标数据丢失**（Pydantic 校验丢弃未知字段）和**地理编码精度不足**（纯名称编码偏差数百米→完整地址编码精确到门口），最终通过微信原生 map 组件 + 高德地理编码实现了带导航跳转的景点路线地图。

---

## 1. 背景需求

旅行规划系统在 result 页面有一个"当日景点路线"模块，原先是静态占位图，显示"地图功能开发中"。需求是将其替换为真实地图——展示当天所有景点的标记点和连线路线，点击标记可跳转导航。

## 2. 难点拆分

### 难点一：坐标数据在后端被丢弃

**现象**：前端拿到的 `dailyPlan[].periods[].items[]` 里没有 `latitude`/`longitude`。

**排查过程**：
1. 后端 Plan 节点的 Prompt 模板确实要求 LLM 输出 `latitude` 和 `longitude` 字段，LLM 也确实输出了
2. `format_node` 的 `_fix_coordinates()` 函数调用高德 MCP `maps_geo` 为每个行程点填充了真实 GPS 坐标，写入 dict 的 `item["longitude"]` / `item["latitude"]`
3. 但是最终返回给前端的 JSON 里这两个字段消失了

**根因**：Python Pydantic v2 默认 `extra="forbid"`（或项目配置了 strict mode），`TimelineItem` Schema 没有定义 `latitude`/`longitude`。`_fix_coordinates` 修改的是 Python dict，但在 JSON 序列化→Pydantic 校验→返回给前端这条链路上，未知字段被静默丢弃了。

**为什么不是代码 bug？**
这是个架构设计问题——代码逻辑是正确的（坐标确实被写入了 dict），但数据校验层和业务逻辑层之间存在信息不对称。`_fix_coordinates` 产出了校验层不认识的字段，就像写了一封信但信封上没写收件人，邮局直接扔掉了。

**解决方案**：
```python
# schemas/trip.py — TimelineItem 加两行
latitude: float | None = None    # GCJ-02 坐标系
longitude: float | None = None
```

**面试可以展开的点**：
- Pydantic `extra` 机制的三种模式：`allow`/`ignore`/`forbid`
- 为什么项目用 `forbid`？防止前端传脏数据，是安全最佳实践
- 这类"跨层数据丢失"问题在微服务/多层架构中很常见，排查思路：逐层打日志

---

### 难点二：地图标记位置不准确（精度从百米优化到十米级）

**现象**：加了坐标字段后，地图上能显示标记点了，但位置明显偏差，部分景点标记跑到了几百米外。

**排查过程**：
1. 首先排除坐标系问题——高德和微信地图都使用 GCJ-02（火星坐标系），不存在转换偏差
2. 检查 `_fix_coordinates` 的地理编码调用：`geocode(f"{city}{item_name}")`
3. 比如故宫 → 实际传的是 `geocode("北京故宫博物院")`
4. 高德收到的请求只有"北京市"+"景点名"，没有区、街道、门牌号
5. 高德只能返回故宫的大概范围坐标（景区中心或正门附近），LLM 填的详细地址如 `"东城区景山前街4号"` 根本没被利用

**根因**：`_fix_coordinates` 只用 `item.get("name")`（景点名）做地理编码，忽略了 `item.get("address")`（详细地址）。高德地理编码的精度直接取决于输入地址的完整度：
```
"北京故宫博物院"              → 景区模糊坐标，偏差 300-500m
"北京东城区景山前街4号故宫博物院"  → 精确到门口，偏差 < 50m
```

**解决方案**：
```python
# 改前：只用 name
def _do_geocode(item_name: str) -> tuple:
    loc = geocode(f"{city}{item_name}")

# 改后：优先用完整 address，没有才回退到 name
def _do_geocode(item_name: str, item_addr: str) -> tuple:
    search_text = f"{city}{item_addr}" if item_addr else f"{city}{item_name}"
    loc = geocode(search_text)
```

**效果对比**：
| 输入 | 故宫坐标精度 | 断桥坐标精度 |
|------|-------------|-------------|
| `北京故宫博物院` | ~400m 偏差 | — |
| `北京东城区景山前街4号` | < 50m | — |
| `杭州断桥残雪` | — | ~200m 偏差 |
| `杭州西湖区北山街断桥残雪` | — | < 30m |

**面试可以展开的点**：
- 地理编码精度取决于地址粒度，这是一个工程常识但容易被忽略
- 为什么不让 LLM 直接生成准确坐标？因为 LLM 有空间性幻觉（spatial hallucination），经常编造看似合理的坐标。`_fix_coordinates` 本身就是对抗幻觉的措施——用真实 API 修正 LLM 输出
- 降级策略：有 address 用 address，没有就用 name（如"酒店午休"本身就是逻辑地点，不需要坐标→直接跳过）

### 难点三：技术选型——微信原生 map vs 第三方 SDK

**选项对比**：

| 方案 | 优点 | 缺点 |
|------|------|------|
| 高德小程序 SDK (`amap-wx`) | 功能丰富（路线规划、POI 搜索） | 额外依赖、包体积 +200KB、需额外申请 Key |
| 腾讯地图 SDK (`qqmap-wx`) | 腾讯生态兼容好 | 项目已从腾讯地图迁出、Key 不通用 |
| **微信原生 `<map>` 组件** ✅ | **零依赖、原生渲染、自动适配深色模式** | 功能有限（仅标记+折线，无路线规划） |

**最终选择**：微信原生 `<map>` —— 我们的需求是"展示当日景点位置 + 点击导航"，标记（markers）+ 折线（polyline）+ `wx.openLocation()` 完全够用，不需要路线规划的 SDK。

**设计决策**：
```javascript
// markers: 每个景点一个标记点，蓝色数字 label + 名称 callout
// polyline: 连接所有标记点的蓝色折线，带方向箭头
// wx.openLocation(): 点击标记 → 微信原生地图 → 用户点"导航" → 自动跳高德/腾讯/百度
```

**为什么不用 `navigateToMiniProgram` 跳转高德小程序？**
- 需要知道高德小程序的 AppId，且用户不一定装了高德
- `wx.openLocation()` 微信自动判断用户装了什么地图 App，更通用

## 3. 完整解决链路回顾

```
LLM 生成 Plan（address + name）
       │
       ▼
format_node: _fix_coordinates()
   ├── 提取 item.name + item.address
   ├── 优先 geocode("北京" + "东城区景山前街4号")  ← 精度优化
   ├── 回退 geocode("北京" + "故宫博物院")
   ├── 跳过非实体地点（酒店午休等）
   └── 写入 item.latitude / item.longitude
       │
       ▼
Pydantic TimelineItem 校验（latitude/longitude 字段已定义）← 数据不丢失
       │
       ▼
JSON → 前端 result 页面
   ├── buildMapData() 解析坐标
   │     ├── 跳过 null/0 坐标
   │     ├── → markers（标记点 + 数字 label）
   │     └── → polyline（路线连线）
   ├── 微信原生 <map> 渲染
   └── 点击标记 → wx.openLocation() → 导航
```

## 4. 面试话术模板

> "这个项目有个地图路线展示的功能，我遇到了一个比较有意思的问题。最开始加了地图组件后发现标记点坐标不准，排查发现两个原因：一个是 Pydantic 校验层把我后端填充的坐标字段丢了，因为 Schema 没定义；另一个是地理编码精度不够，我只用了景点名去编码，偏差几百米，后来改成优先用 LLM 生成的详细地址去编码，精度提到了几十米。这个过程中还做了技术选型——微信原生 map 组件 vs 高德 SDK，最后选了原生组件，因为我们的需求只是展示路线和导航，不需要 SDK 的复杂功能。"
